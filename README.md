# test_memo

**クリーンアーキテクチャ**を学ぶために作った、ターミナルで動くシンプルなメモ帳アプリです。
メモの「作成」「一覧表示」「削除」ができます。

機能はとても小さいですが、あえて役割ごとにファイルを分けています。
このREADMEでは「なぜ分けるのか」「どう分けているのか」を、初めての人にもわかるように順番に説明します。

## 1. まずは動かしてみよう

### 必要なもの
- Python 3.9 以上（`list[Memo]` という型ヒントの書き方を使っているため）
- 外部ライブラリは不要です（Python の標準ライブラリだけで動きます）

### 起動コマンド
`main.py` があるフォルダ（プロジェクトのルート）に移動してから、次のコマンドを実行します。

```bash
cd test_memo
python3 main.py
```

> ⚠️ 各ファイルは `from entities.memo import Memo` のように、ルートフォルダを起点にして他のファイルを読み込んでいます。
> 別のフォルダから実行すると `ModuleNotFoundError` になるので、必ずルートフォルダで実行してください。

### 使い方
起動するとメニューが表示されるので、番号を入力して操作します。

```
=============================
  📝 メモ帳アプリ
=============================
1. メモを作成する
2. メモの一覧を見る
3. メモを削除する
0. 終了
-----------------------------
番号を入力してください：
```

※ メモはパソコンのメモリ上に保存しているだけなので、アプリを終了すると消えます。

## 2. ディレクトリ構造

```

├── main.py                              # 起動役：部品を組み立てて、画面の入出力をする
├── entities/
│   └── memo.py                          # エンティティ層：「メモとは何か」とそのルール
├── usecases/
│   └── memo_usecase.py                  # ユースケース層：「アプリで何ができるか」
├── interfaces/
│   └── memo_repository.py               # インターフェース層：保存係への「約束事」

    └── in_memory_memo_repository.py     # インフラ層：約束事を守る「実際の保存係」
```

フォルダの名前が、そのまま「層（レイヤー）」の名前になっています。

## 3. クリーンアーキテクチャってなに？

### ひとことで言うと
**「アプリを役割ごとに分けて、大事な部分ほど他の部分の影響を受けないようにする」設計の考え方**です。

### 分けないとどうなる？
このアプリは、`main.py` 1つに全部書くこともできます。

```python
# 全部ひとつにまとめた場合のイメージ
memos = {}
title = input("タイトル：")
if len(title.strip()) == 0:      # ルールのチェック
    print("タイトルを入力してください")
else:
    memos[id] = {...}            # 保存の処理
```

小さいうちはこれで問題ありません。でも、アプリが育ってくると困ることが出てきます。

- 「保存先をファイルやデータベースに変えたい」→ あちこちにある保存処理を全部書き換える必要がある
- 「画面をWebにしたい」→ ルールのチェックが `input()` や `print()` と混ざっていて、取り出しにくい
- 「どこに何が書いてあるか」がわからなくなり、1か所直すと別の場所が壊れる

### 分けるとどうなる？
役割ごとに分けておくと、**変更したい部分だけを直せば済む**ようになります。
クリーンアーキテクチャは、そのための「分け方」と「つなぎ方」のルールです。

### レストランでたとえると 🍳
このアプリの構成は、レストランにたとえるとイメージしやすくなります。

| レストラン | このアプリ | 層 |
|---|---|---|
| 料理のレシピと「こうでなければダメ」という決まり | `Memo`（タイトルは空にできない） | エンティティ |
| 料理長：注文を受けて、レシピどおりに調理の流れを進める | `MemoUseCase` | ユースケース |
| 食材業者との契約書：「頼んだら届けてくれること」 | `MemoRepository` | インターフェース |
| 実際の食材業者（A社でもB社でもいい） | `InMemoryMemoRepository` | インフラストラクチャ |
| 開店準備をする人：料理長と業者を引き合わせ、お客さんの注文を受ける | `main.py` | エントリーポイント |

ポイントは、**料理長は「契約書」しか見ていない**ことです。
契約どおりに届けてくれるなら、業者がA社からB社に変わっても、料理長のやり方は何も変わりません。

## 4. このアプリの4つの層

内側から順番に見ていきます。内側ほど「アプリの中心となる大事なもの」です。

### ① エンティティ層（`entities/memo.py`）
**「メモとは何か」を決める層**です。

- メモが持つデータ：ID・タイトル・本文・作成日時
- メモのルール：`is_valid()` で「タイトルは空にできない」ことを確認する

```python
@dataclass
class Memo:
    id: str
    title: str
    content: str
    created_at: datetime

    def is_valid(self) -> bool:
        return len(self.title.strip()) > 0
```

この層は**他のどのファイルも import していません**。画面が何であっても、保存先がどこであっても、「メモとは何か」は変わらないからです。

### ② ユースケース層（`usecases/memo_usecase.py`）
**「このアプリで何ができるか」を決める層**です。

- `create_memo()`：メモを作る → ルールをチェックする → 保存する
- `get_all_memos()`：全部のメモを取り出す
- `delete_memo()`：メモを削除する

ユースケースは「保存する」ことはお願いしますが、**どうやって保存するかは知りません**。
知っているのは、次の「約束事」だけです。

### ③ インターフェース層（`interfaces/memo_repository.py`）
**保存係に対する「約束事」を決める層**です。

```python
class MemoRepository(ABC):
    @abstractmethod
    def save(self, memo: Memo) -> None: ...

    @abstractmethod
    def find_all(self) -> list[Memo]: ...

    @abstractmethod
    def delete(self, memo_id: str) -> None: ...
```

ここには「`save`・`find_all`・`delete` ができること」と書いてあるだけで、中身の処理はありません。
このように中身のないクラスを**抽象クラス**といいます（`ABC` と `@abstractmethod` で作ります）。

### ④ インフラストラクチャ層（`infrastructure/in_memory_memo_repository.py`）
**約束事を守って、実際に保存する層**です。

```python
class InMemoryMemoRepository(MemoRepository):  # 約束事を継承する
    def __init__(self):
        self._store: dict[str, Memo] = {}

    def save(self, memo: Memo) -> None:
        self._store[memo.id] = memo
    ...
```

今回は一番シンプルな「Python の辞書に入れておく」方法で実装しています。
`MemoRepository` を継承しているので、約束した3つのメソッドを必ず実装しなければなりません（実装し忘れるとエラーになります）。

### ＋ エントリーポイント（`main.py`）
厳密には層ではありませんが、**全部の部品を組み立てて、アプリをスタートさせる役**です。

```python
repo = InMemoryMemoRepository()  # 実際の保存係を用意する
usecase = MemoUseCase(repo)      # ユースケースに保存係を渡す
```

そのあとは、メニューを表示してユーザーの入力を受け取り、ユースケースに処理をお願いして、結果を表示します。

## 5. 一番大事なルール：依存の向き

### 「依存する」とは？
あるファイルが別のファイルを `import` して使っていることを、「依存している」といいます。
依存しているファイルは、依存先が変わると影響を受けます。

### ルール：依存は必ず「内側」に向ける
クリーンアーキテクチャでは、層を「玉ねぎ」のように内側と外側に重ねて考えます。

```
外側（変わりやすい）
│
├─ main.py / infrastructure     … 画面の入出力・実際の保存方法
│   │
│   └─ interfaces               … 保存係への約束事
│       │
│       └─ usecases             … アプリでできること
│           │
│           └─ entities         … メモとそのルール（一番大事・変わりにくい）
│
内側（変わりにくい）
```

**外側は内側を知っていてよいが、内側は外側を知ってはいけない**、というのがルールです。

実際に、各ファイルが何を import しているかを見てみると、このルールが守られていることがわかります。

| ファイル | import しているもの |
|---|---|
| `entities/memo.py` | （このアプリのファイルは何も import していない） |
| `interfaces/memo_repository.py` | `Memo` |
| `usecases/memo_usecase.py` | `Memo`、`MemoRepository` |
| `infrastructure/in_memory_memo_repository.py` | `Memo`、`MemoRepository` |
| `main.py` | `InMemoryMemoRepository`、`MemoUseCase` |

図にすると、矢印（＝ import の向き）はすべて中心の `Memo` に向かっています。

```
main.py ──────────────┬──────────────────────┐
                      ▼                      ▼
              MemoUseCase          InMemoryMemoRepository
                      │                      │
                      │ 使う                  │ 継承して実装
                      ▼                      ▼
                  MemoRepository（約束事）◀──┘
                      │
                      ▼
                    Memo
```

### なぜ `usecases` は `infrastructure` を import していないの？
ここがクリーンアーキテクチャで一番おもしろいところです。

ユースケースは保存係を使っているのに、`InMemoryMemoRepository` を import していません。
代わりに、**約束事（`MemoRepository`）を import して、「この約束を守る保存係なら誰でもいい」という書き方**をしています。

```python
class MemoUseCase:
    def __init__(self, repo: MemoRepository):  # ← 約束事の型で受け取る
        self.repo = repo
```

本来なら「ユースケース → 保存係」と依存しそうなところを、間に約束事をはさむことで、
「保存係 → 約束事 ← ユースケース」と、どちらも内側を向くようにしています。
これを**依存性逆転の原則**といいます。

そして、実際の保存係は `main.py` で作って外から渡しています。これを**依存性の注入（DI）**といいます。

## 6. 処理の流れを追ってみよう（メモ作成の例）

メニューで「1. メモを作成する」を選んだときに、どの層をどう通っていくかを見てみます。

```
[ユーザー] タイトル「買い物」、本文「牛乳」を入力
    │
    ▼
① main.py
   usecase.create_memo("買い物", "牛乳") を呼ぶ
    │
    ▼
② usecases/memo_usecase.py
   ・ID（uuid）と現在時刻をつけて Memo を作る
   ・memo.is_valid() でルールをチェックする
    │
    ▼
③ entities/memo.py
   ・タイトルが空でないか確認 → OK なら True を返す
    │
    ▼
④ usecases/memo_usecase.py
   ・self.repo.save(memo) で保存をお願いする
     （このとき、相手が誰かは知らない。約束事どおりに save を呼ぶだけ）
    │
    ▼
⑤ infrastructure/in_memory_memo_repository.py
   ・辞書 self._store にメモを入れる
    │
    ▼
⑥ main.py
   「✅ メモを保存しました：「買い物」」と表示する
```

タイトルが空だった場合は、③ で `False` になり、② で `ValueError` が発生します。
`main.py` がそのエラーを受け取って「❌ エラー：タイトルを入力してください」と表示します。
**ルールを決めるのはエンティティ、ルールを使って判断するのはユースケース、表示するのは main.py**と、役割がきちんと分かれています。

## 7. 分けておくと何がうれしいの？

### うれしいこと① 保存先を簡単に変えられる
例えば「アプリを終了してもメモが消えないように、ファイルに保存したい」と思ったとします。
やることは次の2つだけです。

**1. 約束事を守る新しい保存係を作る**

```python
# infrastructure/file_memo_repository.py（例）
class FileMemoRepository(MemoRepository):
    def save(self, memo: Memo) -> None:
        ...  # ファイルに書き込む処理

    def find_all(self) -> list[Memo]:
        ...  # ファイルから読み込む処理

    def delete(self, memo_id: str) -> None:
        ...  # ファイルから消す処理
```

**2. `main.py` の1行を差し替える**

```python
repo = FileMemoRepository()  # ← ここだけ変える
usecase = MemoUseCase(repo)
```

**エンティティとユースケースは1文字も変更しなくてOK**です。
これが「大事な部分ほど、他の部分の影響を受けない」ということです。

### うれしいこと② 画面を変えても中身はそのまま
今はターミナルで `input()` と `print()` を使っていますが、Web アプリにしたくなっても、
作り直すのは `main.py` の部分だけです。`MemoUseCase` はそのまま使い回せます。

### うれしいこと③ テストがしやすい
ユースケースは約束事さえ守っていれば、どんな保存係でも受け取れます。
そのため、テストのときは本物の保存係の代わりに、テスト用の保存係を渡して動作を確かめることができます。

### うれしいこと④ どこに何があるかすぐわかる
「ルールを変えたい → `entities`」「保存方法を変えたい → `infrastructure`」のように、
直したい内容から、見るべきファイルがすぐにわかります。

> 💡 このアプリくらいの大きさだと、正直「分けすぎ」に感じるかもしれません。
> クリーンアーキテクチャは、アプリが大きくなったときや、長く育てていくときに本領を発揮します。
> 小さなアプリで「形」を体験しておくのが、このプロジェクトの目的です。

## 8. 用語集

| 用語 | 意味 |
|---|---|
| 層（レイヤー） | 役割ごとに分けたコードのまとまり。このアプリではフォルダ1つが1つの層 |
| エンティティ | アプリの中心となるデータと、そのルール。ここでは `Memo` |
| ユースケース | アプリでできる操作（作成・一覧・削除など）の流れ |
| リポジトリ | データの保存・取り出しを担当する係のこと。ここでは `MemoRepository` |
| 抽象クラス | 「どんなメソッドを持つか」だけを決めて、中身は書かないクラス。Python では `ABC` を継承して作る |
| 依存 | あるコードが別のコードを import して使っていること |
| 依存性逆転の原則 | 具体的な実装に直接依存せず、間に「約束事（抽象）」をはさんで、依存の向きを内側にそろえる考え方 |
| 依存性の注入（DI） | 使う部品を、クラスの中で作るのではなく外から渡すこと。ここでは `main.py` で保存係を作って `MemoUseCase` に渡している |

## 9. コードを読む順番のおすすめ

初めて読むときは、**内側から外側へ**の順番がおすすめです。依存が少ないファイルから読むと、理解しやすくなります。

1. `entities/memo.py`：まずは「メモとは何か」を知る
2. `interfaces/memo_repository.py`：保存係への約束事を知る
3. `usecases/memo_usecase.py`：約束事を使って、どんな操作ができるかを知る
4. `infrastructure/in_memory_memo_repository.py`：約束事が実際にどう実装されているかを知る
5. `main.py`：全部がどう組み立てられて動いているかを知る

各ファイルには、処理の意味を説明するコメントを書いてあるので、あわせて読んでみてください。
